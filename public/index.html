SealBox

Seal a file to Shelby and record a signed, independently verifiable manifest entry for it.

v0.3.0 TypeScript CLI Ed25519 MIT

SealBox is a command-line tool, not a web app — this page only describes it. Everything below is a claim the code backs up, or an honestly-labelled limitation.

What a PASS proves

When sealbox verify <sealId> prints PASS, the code has checked:

  • Content integrity — the bytes retrieved from storage hash to the recorded SHA-256 and match the recorded size.
  • Signature authenticity — the recorded Ed25519 signature verifies cryptographically against the stored public key, over a canonical, domain-separated signed record.
  • Signer consistency — the stored signer address is the one derived from the stored public key.

Cryptographic validity vs. signer trust

A PASS establishes cryptographic validity and signer consistency. It does not establish signer trust: SealBox does not decide whether a key is one you should trust. Compare the reported public key and address against a key you already trust out of band — that decision is the verifier's, by design.

Install

git clone https://github.com/Rishidar-lab/sealbox.git
cd sealbox
npm ci
npm run build
npm link            # optional: puts `sealbox` on your PATH

Use

sealbox seal ./report.pdf     # hash, upload, sign, record
sealbox verify <sealId>        # re-fetch, re-hash, verify signature + signer
sealbox list                  # every record in the local manifest
sealbox doctor                # preflight: local config and live network

Live Shelby status

Upload proven on the live network · round trip not yet complete.

A real Ed25519-signed artifact was uploaded through the official self-hosted S3 gateway (HTTP 200, on-chain registration). Retrieval currently fails because the anonymous tier stores blobs un-encoded — the official SDK reproduces this with no SealBox in the loop, so it is upstream behaviour, not a SealBox defect. The remaining input is a Shelby API key. See the repository's blocker note.

What SealBox does not prove

It makes no claim of trusted timestamping, indefinite storage, third-party notarization, or anything about the truth, safety, legality or ownership of the sealed bytes. The full list is in the README. The cryptography has not been externally audited.
